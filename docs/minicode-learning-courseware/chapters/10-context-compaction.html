4.1 上下文治理：长任务为什么不会轻易爆掉

学习目标

  • 理解 Coding Agent 为什么特别容易上下文爆炸。
  • 掌握 MiniCode 的上下文压缩链路。
  • 区分 Micro Compact、Auto Compact 和 Reactive Compact。

上下文爆炸来自哪里

Coding Agent 的上下文增长速度比普通聊天快得多，因为它会不断产生：

  • 用户需求和澄清。
  • 模型推理过程。
  • 文件读取结果。
  • grep 搜索结果。
  • 命令和测试输出。
  • Git diff。
  • 工具错误堆栈。
  • 中间计划和验证记录。

如果全部塞进 messages，很快超过模型窗口。

ContextManager

context_manager.py 负责基础上下文管理：

  • 模型 context window 识别。
  • token 估算。
  • CJK 友好的 token 估算。
  • context stats 统计。
  • 多级摘要压缩。
  • 老消息摘要和保留近期关键消息。

它回答的是：“当前上下文用了多少，还能不能继续？”

ContextCompactor

context_compactor.py 是更接近 Claude Code 风格的压缩编排器。ContextCompactor.process_request 的流程：

messages
  -> Tool Result Budget: 大工具结果外置化/替换
  -> Read Dedup: 处理重复读文件结果
  -> Microcompact: 清理陈旧可压缩内容
  -> Auto Compact: 高水位触发 session/full compact
  -> Reactive Recover: API 报 prompt-too-long 后兜底恢复

Tool Result Budget

工具结果可能非常大，例如读大文件、跑测试、搜索仓库。MiniCode 会把过大的工具结果持久化到本地，再在上下文中保留摘要或引用，减少 prompt 压力。

这个思想和 RAG 中“文档块不全部塞进 prompt，只塞相关片段”有点像，但对象从知识库文档变成了 Agent 工具结果。

Read Dedup

如果 Agent 多次读取同一个文件，重复内容会浪费大量上下文。Read Dedup 的目标是识别重复读文件结果，减少重复传输，同时保留必要的引用信息。

Micro Compact / Auto Compact / Reactive Compact

类型触发时机解决问题
Micro Compact平时、轻量、时间或预算驱动清理陈旧工具结果，低成本释放空间
Auto Compact上下文接近阈值主动压缩历史消息，避免请求失败
Reactive CompactAPI 已经报超限紧急截断/压缩，恢复请求能力

难点：压缩不能丢任务状态

长上下文治理最难的是：不能为了省 token 把任务目标、文件变更、用户约束、验证结果压没。MiniCode 通过 working memory、stable task pack、session memory compact 等方式保护关键状态。

本章小结

MiniCode 的上下文治理不是“超过就摘要一下”，而是一条分层 pipeline：先预算和去重，再轻量压缩，再主动 compact，最后 reactive recover。它体现了把上下文当成有限资源治理的思路。
