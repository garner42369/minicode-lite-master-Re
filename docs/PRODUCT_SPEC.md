# MiniCode 产品规格（PRODUCT_SPEC）

> Day 1 冻结产品边界。本文档回答：MiniCode 是什么、第一版不是什么、成功如何证明。
> 它是活文档，会随 30 天复现逐步细化；但「边界」和「验收故事」一旦冻结，改动需在 DECISIONS.md 记录。

## 一句话定位

MiniCode 是一个面向真实代码仓库的本地 AI Coding Agent Runtime：
接收用户自然语言任务，调用模型推理，通过受控工具读取代码、修改文件、执行命令、运行测试，
并在长任务中处理上下文、记忆、权限与恢复问题。

它要解决的主问题是：**让大模型在真实开发环境里安全、连续、可恢复地干活**，
而不是「让大模型回答知识库问题」（那是 RAG）。

## 是什么 / 不是什么

| 是 | 不是 |
| --- | --- |
| 本地 Agent 运行时 | 网页聊天机器人 |
| 模型提议 + 受控执行 | 模型直接改文件 |
| 可观察、可恢复、可验证 | 一次性 API 调用 |
| 自研主链路（无 Agent 框架） | LangChain/LlamaIndex 示例 |

## 核心用户故事

主线故事（贯穿全程的验收锚点）：

```text
用户要求修复失败测试
→ Agent 找到测试和实现
→ 运行测试取得失败证据
→ 申请并实施最小修改
→ 再次运行测试
→ 以实际结果结束，而不是以模型口头声明结束
```

配套的演示仓库 `tests/fixtures/buggy_calculator/` 承载这条故事：
`calculator.py` 的 `divide(a, b)` 把真除法 `/` 误写成整除 `//`。

## 四种停止结果

一次任务最终落入四种结果之一（对应 Day 1 的 `Outcome` 枚举）：

| 结果 | 枚举 | 含义 |
| --- | --- | --- |
| 验证通过 | `VERIFIED` | 修改后有证据证明任务完成（如测试通过） |
| 失败 | `FAILED` | 尝试后无法完成，或有证据表明失败 |
| 等待用户 | `AWAIT_USER` | 需要用户确认/审批/补充信息才能继续 |
| 预算耗尽 | `BUDGET_EXHAUSTED` | 达到步数/上下文/成本上限仍未完成 |

> 注意：模型口头说「完成」不等于 `VERIFIED`。运行时可能在 Day 14（验证门槛）判定「未验证」。

## 验收故事（可执行）

每条故事至少声明：用户输入、预期变更、验证命令、预期结果。

| 故事 | 用户输入 | 预期变更 | 验证命令 | 预期结果 |
| --- | --- | --- | --- | --- |
| 修复失败测试 | 修复 divide 的失败测试 | `calculator.py` 整数除法改为真除法 | `pytest tests/test_calculator.py -q` | `VERIFIED`（2 passed） |
| 拒绝越权编辑 | 修改工作区外文件 | 任何文件都不改变 | 比对工作区哈希 | `AWAIT_USER` |

## V0 暂缓项（不阻塞第一版）

以下能力明确不在 V0（离线可解释 Agent）范围内，后续版本再引入：

- TUI（Day 22）
- MCP 外部工具服务器（Day 24）
- 向量检索（Day 20）
- 控制论增强层（Day 27–29）

Day 1 的系统尚不能自动完成上述修复路径；这正是后续 30 天要逐步构建的能力。
